# Inspect Web public-evidence bridge

## Status and authority

This document defines the Inspect Web public-evidence bridge: the narrow
same-origin transport used when a product-owned Browser/Wasm operation needs a
fixed public provider whose response is not browser-CORS-readable. Its first
consumer is Package Changes, tracked by
[#7037](https://github.com/richlander/dotnet-inspect/issues/7037) as a
prerequisite to step 7 of the eight-step
[#6124](https://github.com/richlander/dotnet-inspect/issues/6124) adoption
plan.

Its claim is:

> A Browser/Wasm operation can acquire bounded JSON from an explicitly named
> public provider through Inspect Web's same-origin managed API without giving
> the caller authority to choose an upstream destination or weakening the
> provider identity and failure semantics consumed by product code.

The bridge owns its fixed upstream request shapes, Browser rewrite,
same-origin routes, response bounds, and transport-failure mapping. It does not
own NuGet Catalog traversal, GitHub advisory evidence, package-change request
or report semantics, source identity, Worker operation delivery, Browser
state, rendering, route placement, provider caching, or a general proxy.

The existing MSDL symbol bridge is analogous deployment evidence, not part of
this owner. It uses the same managed Function app because Azure Static Web Apps
deploys one managed API with the site, but its request grammar, response
content, and bounds remain independently owned.

## Motivation and evidence

The package-change report's real production scenario includes
`Microsoft.Extensions.AI@10.10.0` in the product-owned
Microsoft.Extensions population. The report must acquire NuGet.org's service
index, Catalog index and pages, matching Package Details leaves, and
GitHub-reviewed NuGet advisory documents.

On September 15, 2026, requests carrying
`Origin: https://dotnet-inspect.net` to these provider URLs returned JSON
without an `Access-Control-Allow-Origin` response header:

```text
https://api.nuget.org/v3/index.json
https://api.nuget.org/v3/catalog0/index.json
https://api.github.com/advisories
```

The observation is reproducible with:

```bash
curl -fsS -D - -o /dev/null \
  -H 'Origin: https://dotnet-inspect.net' \
  https://api.nuget.org/v3/catalog0/index.json
```

This establishes the Browser transport need. It does not establish provider
availability, latency, completeness, or report correctness.

The conventional response to a public API that does not permit browser CORS is
a same-origin backend-for-frontend endpoint. This repository deliberately uses
a stricter form: provider, method, path, query grammar, response media, and
response size are closed rather than accepting a caller-supplied URL.

## Boundary and authority

An internet caller can invoke the anonymous managed-API routes directly. The
request path and query cross the Inspect Web Function boundary to public
NuGet.org or GitHub infrastructure. The containment invariant is:

> Every outbound request is a credential-free `GET` constructed from a
> compile-time HTTPS origin and an admitted provider-specific path or query;
> no caller input can select another scheme, authority, port, method, body,
> fragment, or request header.

The Function rejects an invalid request before outbound traffic. It does not
sanitize an invalid value into a nearby request. It forwards no incoming
cookie, authorization value, referrer, user agent, or other caller header.
Redirect following is disabled so a provider response cannot choose another
destination.

The two admitted request families are:

- the canonical NuGet.org v3 service index and Catalog index, page, and
  Package Details leaf paths under `api.nuget.org`; and
- the GitHub `api.github.com/advisories` reviewed-NuGet query generated by the
  advisory-evidence owner, with its optional `after` continuation.

The advisory route accepts exactly the fixed category controls plus a bounded
comma-separated package-ID population and an optional bounded cursor. The
NuGet route accepts no upstream query. Neither route accepts an arbitrary URL.

The Browser transport rewrites only canonical HTTPS requests for those two
families to the current site's absolute managed-API routes. After transport it
restores the logical provider request URI on the response. Product-owned
source and advisory validation therefore continues to observe the real
provider identity rather than the implementation-only same-origin hop.

## Response and failure contract

Only an HTTP 200 JSON response becomes a successful bridge result. The Function
checks the declared length and actual decoded body size before publishing
success:

| Provider response | Maximum decoded body |
| --- | ---: |
| NuGet service-index or Catalog document | 16 MiB |
| GitHub advisory document | 4 MiB |

These are the existing consumer-owner per-document limits, not new report-wide
budgets. The report's aggregate Catalog and advisory limits continue to apply
after the bridge.

The advisory route preserves the provider's `Link` response header so the
advisory owner can validate and follow an exact continuation. It preserves no
other provider header. Every managed response receives the Function-owned
security headers and `Cache-Control: no-store`; the bridge introduces no cache
freshness claim.

Provider non-success status remains a non-success status. A declared or
observed oversized response becomes `413`; a transport failure becomes `502`;
and an upstream timeout becomes `504`. Caller cancellation publishes no
replacement result. Wrong media, an unexpected successful status, and an
invalid continuation-header shape become visible bridge failures rather than
empty JSON.

## Composition and non-claims

The package-change Browser adapter will construct a canonical NuGet.org v3
client over the Browser rewrite and a
`GitHubNuGetAdvisoryService` over the same fixed-provider transport. Those
owners retain their producer identities, request bounds, parsing, evidence,
and failure classifications. This bridge does not reproduce or reinterpret
their payloads.

Package-change Worker streaming and Browser presentation remain follow-on work
under the ecosystem-report and Browser operation owners. This slice does not
make Package Changes user-visible, add a query mode, or claim the complete
Browser adoption step.

The bridge is host-specific rather than shared product substrate: the CLI can
contact both public providers directly and does not need a same-origin hop.
The user's approved Browser adoption in #6124 is the single-host basis.

## Verification

Release gates must establish:

- invalid NuGet paths and advisory queries issue no outbound request;
- admitted requests construct only the two compile-time provider origins;
- redirects are not followed and incoming credentials or arbitrary headers
  are not forwarded;
- JSON success, advisory continuation, provider status, timeout, transport
  failure, wrong media, and declared or observed oversize remain distinct;
- every handled Function outcome carries the managed-API security and
  no-store headers;
- the Browser handler rewrites only canonical provider requests to the
  configured origin and restores logical provider identity after transport;
  and
- another destination, method, provider path, or malformed origin remains
  unchanged or is rejected as specified, never redirected through the bridge.

These gates enforce this owner's construction and transport claims. The
existing Package Changes query, presentation, CLI, and later real-Wasm gates
remain responsible for report semantics and production-host behavior.
